# evals — регресс-набор кита

Проверяет, что правила кита доезжают до рабочей сессии и не противоречат друг другу.
Критерии провала объявлены в `criteria.md` **до** прогонов; отчёты — в `results/`.

```bash
./evals/run.sh mech       # механические: секунды, бесплатно — гонять перед каждым релизом
./evals/run.sh sessions   # четыре сессионных прогона, read-only, ~8 мин параллельно
./evals/run.sh all
```

- `mech/` — юнит-тесты правил: проверка ledger из Phase 7 на четырёх состояниях (включая
  `half-migrated`, на котором прежние грепы давали ложный зелёный), согласованность `rules` с
  прозой, целостность ссылок и локстеп версий.
- `fixtures/` — четыре проекта-шаблона: однозначная спецификация (тест на церемонию), проект без
  ledger (тест на ложный finding §11), проект с owner-развилками равной цены (тест authority),
  проект-соблазн переименовать реализацию в spike.
- `results/REPORT.md` — прогон v1.21.2: 9/9 механических, 4/4 сессионных.
- `results/ABLATION.md` — попытка измерить **пользу**, а не доставку: плечо без доступа к киту.
  Главный вывод там честный и неудобный — способность заметить owner-вопрос даёт не кит.

Что набор НЕ проверяет: полезность правил при отсутствии операторского baseline §1–8.
Для этого нужен чистый профиль с собственной аутентификацией либо штатный
`claude plugin eval --ablation` (сейчас early access).
