# Мануал — работа по обвязке

[English](manual.md) · **Русский**

Что вводить, когда и что проверять — от первой установки до шестого месяца проекта. Вы работаете
над своим проектом, а способ работы несут команды, поэтому думать о том, как заставить агента
работать хорошо, не нужно.

## Ваша последовательность

| Ситуация | Что вводить |
|---|---|
| Начало любой сессии — или когда не уверены, что дальше | `/harness:start` |
| Новое изменение | `/harness:task <что нужно>` |
| Баг | `/harness:bugfix <баг>` |
| Сырая идея, которую сначала хочется обсудить или прожарить | `/grill-with-docs <идея>`, затем `/harness:task` |
| Рискованное изменение собрано | `/harness:check` (обычное изменение — `/code-review`) |
| Конец сессии | `/harness:wrap` |
| Работа не на одну сессию | `/harness:task` → `/to-spec` → `/to-tickets` → `/harness:wrap`; затем на каждый тикет: `/harness:tests <тикет>` и в свежей сессии `/harness:build <тикет>` |
| Задача наконец решена после долгих поисков или повторяется снова и снова | `/harness:skill <что делает>`, позже `/harness:trajectory` |

`/harness:start` читает репозиторий и говорит, какая из этих команд следующая, с уже подставленным
аргументом. Команды `/harness:*` несут в себе измеренные промпты, поэтому ничего длинного вводить
руками не надо; в контексте они ничего не стоят, пока вы их не вызвали.

Промпты интервью, ревью и исправлений внутри команд — те самые, что измерялись; команды тестов и
сборки переносят измеренные промпты (для целой спеки) на один тикет. Блок *How we work* в
`CLAUDE.md` держит тот же поток и без команды: на обычный запрос сессия интервьюировала, писала
спеку и отчитывалась командой тестов с её выводом в 9 из 9 прогонов. Измеренного прироста качества
команды к этому не добавляют; они нужны, чтобы вы всегда знали, что ввести дальше.

## Установка

**Один раз на машину.**

```
/plugin marketplace add nikitaCodeSave/claude-code-harness
/plugin install harness@claude-code-harness
/plugin install mattpocock-skills --marketplace mattpocock/skills
```

То, что вы ставите из `/plugin`, начинает действовать, когда закрывается его меню.

В README Pocock есть ещё путь через официальный каталог, `mattpocock-skills@claude-plugins-official`.
Выберите один путь. Не копируйте скиллы в проект ещё и через skills.sh и не включайте плагин в
аккаунте claude.ai, который синхронизирует его в терминальные сессии как `mattpocock-skills@synced`:
в обоих случаях каждый скилл окажется дважды.

Затем в **пользовательских** настройках (`~/.claude/settings.json`):

```json
{
  "permissions": { "deny": ["Skill(mattpocock-skills:tdd)"] },
  "extraKnownMarketplaces": {
    "claude-code-harness": {
      "source": { "source": "github", "repo": "nikitaCodeSave/claude-code-harness" },
      "autoUpdate": true
    },
    "mattpocock": {
      "source": { "source": "github", "repo": "mattpocock/skills" },
      "autoUpdate": true
    }
  }
}
```

Запрет блокирует `/tdd` и по короткому имени. `autoUpdate` включает обновления для обоих сторонних
маркетплейсов — по умолчанию они выключены. Если в ваших настройках задан `DISABLE_AUTOUPDATER`,
`DISABLE_UPDATES` или `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, автообновление плагинов выключено,
пока вы не добавите `"FORCE_AUTOUPDATE_PLUGINS": "1"` в `env`. Добавьте эти ключи в существующий
файл, не заменяйте его.

**Один раз на проект.** Откройте Claude Code **в корне репозитория** и скажите:

> set up Claude Code harness in this project

Скилл прочтёт репозиторий, выберет путь (новый / существующий / с обвязкой), спросит только то,
чего не видно из кода, и передаст работу. Затем один раз запустите `/setup-matt-pocock-skills`: он
запишет трекер (GitHub, GitLab или локальные файлы), метки триажа и где лежат доменные документы.

**Каждая сессия стартует из корня репозитория.** Список запретов из `.claude/settings.json`
читается из каталога, где стартует сессия. Сессия, запущенная внутри пакета, работает без него.

## Новое изменение — одна сессия

```
/harness:task  →  ответы на вопросы  →  просмотр спеки  →  сборка в той же сессии
   →  «готово» с командой и выводом  →  /code-review или /harness:check  →  /harness:wrap
```

**1. `/harness:task <что нужно>`.** Скажите, что хотите, своими словами, на любом языке, и какой
интерфейс уже зафиксирован (модуль, сигнатура, тип ошибки).

**2. Отвечайте на вопросы.** Здесь уходит ваше время, и именно этот шаг окупается. Если владелец не
правит итоговый отчёт агента: без интервью полная приёмка в 3 из 9 прогонов, с ним — в 7–9 из 9.
Владелец, который правил отчёт, получал 5 из 9 без интервью — за счёт того, что правил сам. Решения
«на будущее» называйте сейчас, один раз.

**3. Просмотрите спеку, когда она появится.** Проверьте три вещи:
- зафиксированный вами интерфейс записан слово в слово;
- non-goals — ваши;
- каждый критерий — то, на чём тест может упасть.

Поправьте сейчас — это самый дешёвый момент. Одна выпавшая строка интерфейса однажды обнулила набор
приёмочных тестов.

**4. Дайте собрать в той же сессии.** Не делайте `/clear` между спекой и сборкой. Та же сессия держала
полную приёмку в 8 из 9 прогонов — самый дешёвый поток с таким результатом; свежая сессия, собирающая
только по файлу, — 7 из 9. Один исполнитель — никакого веера субагентов на изменении такого размера.

**5. Прочтите «готово».** В нём должны быть команда и её вывод. «Тесты проходят» без вывода — это не
готово; попросите: `Show the command you ran and its output.`

**6. Ревью по уровню риска.**
- **Обычное изменение:** `/code-review` на дифф. На среднем effort он сообщает ещё о чистке кода и о
  соглашениях из `CLAUDE.md`; исправляйте то, что влияет на корректность, остальное — по желанию.
- **Рискованное изменение** — безопасность, миграции, парсеры, инварианты, всё, что «выглядит
  готовым» и дорого обойдётся, если неверно: `/harness:check`. Свежий ревьюер только для чтения,
  не видевший рассуждений сессии, проверяет дифф против спеки; сессия воспроизводит каждую находку
  до правок, исправляет настоящие и отклоняет остальные, не больше трёх раундов. Измеренное ревью
  шло в отдельной сессии; команда использует свежего субагента по той же причине — ревьюер не видел
  рассуждений.

**7. `/harness:wrap`.** Решения и термины, которые сессия ещё не записала, вывод проверки, закрытие
сданной или отменённой работы, что осталось, и коммит, где сказано, что изменилось и почему, — включая каждый
удаляемый файл.

## Сырая идея — сначала обсудить

Когда сама идея не устоялась или вы хотите прожарить её до всякой спеки, начните с грилинга Pocock и
собирайте в той же сессии:

- `/grill-with-docs <идея>` — неотступное интервью, которое по ходу записывает термины в
  `GLOSSARY.md` и решения в ADR;
- `/grill-me` — то же интервью, когда вопрос не про этот код.

Затем `/harness:task` в той же сессии: он спросит только то, чего спеке ещё не хватает, напишет её и
соберёт. Грилинг перед сборкой отдельно не измерялся; интервью внутри `/harness:task` — измеренный
вариант по умолчанию для уже понятной задачи.

## Баг

`/harness:bugfix <что происходит, что должно происходить>` — агент сначала воспроизводит баг
падающим тестом, показывает падение, затем исправляет и показывает, что тот же тест проходит. Это
диагностика, а не ритуал test-first. На трудном баге агент может сам подключить `diagnosing-bugs`.
Закончите `/harness:wrap`.

## Работа не на одну сессию

Пользуйтесь этим, только когда работа действительно не помещается в одну сессию. Признаки:
- сессия сама так говорит (блок *How we work* просит её об этом);
- в спеке несколько независимых результатов;
- контекст заполняется ещё до начала сборки.

На фичах, помещавшихся в одну сессию, поток по тикетам (без сессии с тестами, описанной ниже) стоил в
11 раз дороже основного потока, потребовал впятеро больше ходов владельца и потерял решение — поэтому
он для работы, которая действительно не помещается.

**1. Договоритесь, затем нарежьте.** `/harness:task` (или грилинг) выясняет, что нужно; остановитесь до
сборки. С трекером `/to-spec` пишет спеку в него из разговора; без трекера пусть сессия напишет
`specs/<slug>.md`. Затем в том же контексте `/to-tickets`: вертикальные срезы, каждый на одну свежую
сессию, с объявленными блокерами. Каждое решение попадает в ADR, как только устоялось; закончите
`/harness:wrap` — он поймает пропущенные до того, как вы уйдёте. Решение, записанное где угодно, кроме ADR, — даже заметкой «вне рамок» в спеке, — могут
переспросить в следующей сессии и снять, если владелец о нём забыл.

**2. На каждый тикет — две сессии.**
- `/harness:tests <тикет>` в отдельной сессии. Тесты по критериям тикета, пока падающие; каждый
  должен падать на своём assert, а не на ошибке импорта — это заодно ловит критерий, выполненный уже
  на базовом коммите. Команда коммитит тесты и даёт вам id коммита.
- `/harness:build <тикет>` в свежей сессии. Собирает по этим тестам, не трогая их, показывает через
  `git diff`, что они не изменились, и коммитит. Затем закройте тикет — `/harness:wrap` это
  предложит, — потому что открытый тикет держит в ожидании те, что он блокирует.

  Чтобы тесты гарантированно нельзя было править, запустите эту сессию так:

  ```
  claude --settings '{"permissions":{"deny":["Edit(./tests/acceptance/**)","Bash(chmod:*)"]}}'
  ```

  Запрет останавливает инструменты правки и распознаваемую запись из shell (перенаправления, `tee`,
  `sed -i`), но не скрипт, который сам открывает файл, — поэтому сборка ещё и показывает `git diff`.

- `/harness:check`, если тикет рискованный, затем `/harness:wrap`.

Почему две сессии: приёмочные тесты, написанные по спеке отдельной сессией и закрытые для исполнителя
на запись, дали лучший измеренный результат (9 из 9). На уровне тикета это расширение того
результата; отдельно оно не измерено.

**Один тикет за раз.** `/implement-spec` собирает готовые тикеты параллельно. В лаборатории пайплайн,
запускавший 12–22 субагента вместе с грилингом, тикетами и `/tdd`, стоил в 3.1–4.4 раза дороже
последовательного потока при той же приёмке (эти факторы не разделены); контролируемое внешнее
исследование, где параллельность изолирована, показало, что параллельные субагенты решают
ограниченные задачи хуже.

## Обвязка растёт вместе с проектом: проектные скиллы

Обвязка продакшн-проекта растёт вместе с ним — не при установке, а из задач, которые проект
действительно решил. Задача, которую долго нащупывали, или задача, которая возвращается снова и
снова, становится проектным скиллом в `.claude/skills/`, который коммитится вместе с проектом, —
и следующая сессия делает её сразу.

1. **Решите задачу в сессии**, сколько бы это ни заняло, пока результат не станет правильным.
2. **`/harness:skill <что он должен делать>`** в той же сессии. Агент пишет скилл из всего, что
   сессия узнала: когда его применять, самый короткий путь, который сработал, входные данные, куда
   идут результаты, проверку, доказывающую успех, и ловушки, на которые наткнулся, — в виде логики,
   а не кучи примеров.
3. **Запустите ту же задачу в свежей сессии** со скиллом. Правильный ответ будет, но часто окольным
   путём.
4. **`/harness:trajectory`** в этой сессии. Агент перечисляет все вызовы инструментов по порядку — что
   взял из каждого и куда положил, — отмечает лишние, пишет самую короткую цепочку, какой прошёл бы
   человек, и меняет логику скилла так, чтобы вести к ней. Вы подтверждаете дифф.
5. **Повторяйте 3–4**, пока прогон не пойдёт по самой короткой цепочке. Повторяйте снова, когда скилл
   разрастается.

Помощники, которые пишут и проверяют скиллы лучше голого промпта, — команда использует тот, что
установлен:

- [`skill-conductor`](https://github.com/smixs/skill-conductor) — сначала архитектура скилла, потом
  эвалы и контролируемый цикл улучшений;
- [`developing-ai-agents`](https://github.com/ilkruglov/developing-ai-agents-skill) — проектирование
  и отладка агентов, когда скилл сам гоняет агентный цикл;
- `writing-for-agents` из mattpocock-skills — уже установлен;
- `skill-creator` из каталога плагинов Anthropic.

Ни один из них, как и сама процедура, в лаборатории не измерялся. Для скилла, от результата которого
многое зависит, напишите несколько эвалов до тонкой настройки — проверка, которая может упасть,
важнее гладкой траектории.

Рядом с этим `/retro`: после сессии, которая далась тяжелее, чем следовало, он предлагает проверки и
указатели для окружения, а не скилл.

## Другие ситуации

| Что у вас | Что вводить | Пояснение |
|---|---|---|
| Большая задача, путь к которой пока не виден | `/wayfinder` | Составляет тикеты-решения и разбирает их по одному. Планирует, но не собирает. |
| Решение, которое может принять только другой человек | `/to-questionnaire` | Превращает его в опросник для этого человека. |
| Объяснение не дошло | `/wait-what` | Пересказывает его с недостающим контекстом, словами глоссария. |
| Баг-репорты и запросы от других людей | `/triage` | Тикетам, которые вы сгенерировали сами, там не место. |
| Сессия далась тяжелее, чем следовало | `/retro` | Предлагает проверки и указатели; выбираете вы. Проверка, которая может упасть, лучше новой строки прозы. |
| Вопрос дизайна, который разговором не решить | попросите одноразовый прототип | `prototype` вызывается моделью. |
| Кодовая база похожа на кашу | `/improve-codebase-architecture` | Обзор с кандидатами; каждый возвращается в основной поток. Здесь не измерялся. |
| Работа переходит к коллеге, в другой каталог или в другую обвязку | `/handoff` | |
| Непонятно, какой скилл Pocock подходит | `/ask-matt` | Маршрутизирует по скиллам Pocock; этот поток покрывает `/harness:start`. |

## Знания между сессиями

Проекту, над которым работают месяцами, нужно, чтобы каждая новая сессия начиналась с его языка и
его решений, а не с первого разговора. Обвязка держит их в версионируемых файлах:

- **Термины** → `GLOSSARY.md` или `GLOSSARY-MAP.md` со ссылками на глоссарий каждого bounded context.
- **Решения**, которым должна следовать дальнейшая работа, включая сказанные «на будущее» →
  `docs/adr/` или журнал решений, который проект уже ведёт; записываются, когда приняты, и входят в
  коммит с изменением, которое их применяет.
- **Процедуры**, которые проект уже решил, → проектные скиллы в `.claude/skills/`.
- **Перед изменением области** сессия читает статьи глоссария и ADR, которые её касаются, пропуская
  помеченные deprecated или superseded.
- **Текущая работа** живёт в открытой спеке или трекере. Больше нигде.
- **Изменённое решение** → новое ADR; статус старого становится `superseded by NNNN`. Строка статуса —
  единственная правка, которую принимает принятое ADR.
- **Сданная или отменённая работа не оставляет файлов.** Файл сданной и прошедшей ревью спеки
  уходит, когда каждая её строка живёт в тесте, ADR, глоссарии или сообщении коммита; спека в трекере
  закрывается там. Работа, которую вы явно
  отменили, уходит тоже — спека, тикеты (`wontfix`), приёмочные тесты и код; запрос, отклонённый
  насовсем, уходит в `.out-of-scope/`. Исследование в `docs/research/` живёт, пока его решение не
  записано. `/harness:wrap` предлагает каждое удаление и выполняет его после вашего подтверждения,
  сначала коммитя работу. История — в git, папок-архивов нет.
- **Без авто-памяти.** Шаблон настроек её выключает: память, которую Claude пишет сам вне ревью,
  держится за факты, которые проект уже пересмотрел.

`/harness:wrap` в конце каждой сессии ловит ещё не записанные термины и решения и закрывает сданную
или отменённую работу.

Что измерялось: три фичи в новых сессиях, владелец ни разу не повторял прежних решений.
- Передовая модель сохранила их в 3 из 3 прогонов и без этих правил — записала сама.
- С правилами — тоже 3 из 3, примерно на 17% дороже.
- В одном дымовом прогоне более слабая модель выдержала 8 из 19 проверок без правил и 18 из 19 с ними.

Так что правила — страховка. Месяцы накопления — десятки фич, разрастающийся файл спеки — не
моделировались.

## Контекст на границах фаз

| Граница | Что делать |
|---|---|
| Интервью → спека → сборка | Продолжать в той же сессии (измерено выше). |
| Грилинг → `/harness:task` | Продолжать — договорённости и есть вход. |
| `/to-spec` → `/to-tickets` | Продолжать — один контекст. |
| Сессия тестов → сессия сборки | Новая сессия: исполнитель не должен сам писать свой оракул. |
| Тикет → следующий тикет | Новая сессия; каждый тикет самодостаточен. |
| Сессия ждёт | Большая сессия, простоявшая около часа, сжимается сама; вернувшись, введите `Re-read specs/<slug>.md before continuing.` или отключите это в `/config` → Idle compaction. |
| Контекст разрастается | В середине фазы — продолжайте или отдайте ограниченный кусок субагенту. На границе — лучше продолжить или `/clear`; `/compact` — последний вариант (`ask-matt` у Pocock). После любого сжатия введите `Re-read specs/<slug>.md before continuing.` Рамки задачи хранятся в файле спеки, потому что, по сообщениям, сжатие теряет их чаще, чем требования, — это одно внешнее исследование, здесь не проверенное. |

## Большие многосоставные репозитории

- **Стартуйте из корня.** `CLAUDE.md` компонента загружается, когда работа касается его каталога, так
  что его команды и инварианты ничего не стоят в остальное время.
- **Контракты между компонентами — самый рискованный шов.** Изменить контракт — значит сначала
  записать ADR и обновить проверку, которую запускают обе стороны. Пути контрактов в настройках — под
  `ask`.
- **Тикеты остаются вертикальными срезами**, даже если результат затрагивает несколько компонентов.
- **Командам:** держите короткий `REVIEW.md` от владельцев кода — как здесь выглядит провал, какие
  пути всегда требуют человека, лимит на мелочи. Держите его обычным файлом: сервис ревью пропускает
  файл-симлинк и обрезает файл сверх лимита размера.
- **Кто ревьюит, определяет риск, а не автор** (по описанию того, как ревьюит команда Claude Code в
  Anthropic):

  | Риск | Ревьюеры |
  |---|---|
  | Низкий | Зелёные автоматические проверки |
  | Средний | Один человек |
  | Высокий | Два человека |

  Чувствительные пути и CI-процессы всегда требуют человека. Человек, направлявший агента, считается
  одним из ревьюеров; одобрение агента за одобрение человека не считается.

## Не делайте

| Не делайте | Почему |
|---|---|
| Не используйте `/tdd` и не предписывайте исполнителю red-green-refactor | Поток без этого ритуала дал mutation score в пределах 0.05 от пайплайна с `/tdd`. В его наборе были приёмочные тесты из отдельной сессии, так что сравнение — «независимые тесты без ритуала» против «ритуала». Внешнее исследование не нашло выигрыша от test-first при расходе токенов в 3–8.5 раза больше. Тесты, заранее написанные *другой* сессией, и падающая проверка до исправления бага — это не тот ритуал. |
| Не используйте поток по тикетам для работы на одну сессию | В 11 раз дороже, впятеро больше ходов владельца и одно потерянное решение (выше). |
| Не запускайте параллельных исполнителей на ограниченном изменении | См. «Один тикет за раз». |
| Не собирайте в свежей сессии только по файлу спеки | 7 из 9 против 8 из 9 в сессии, которая её писала. Если нужна свежая — сначала напишите приёмочные тесты (9 из 9). |
| Не принимайте «тесты проходят» без вывода | Это заявление, а не доказательство. |
| Не продолжайте ревью, пока ревьюер не будет доволен | Ревьюер, которого просят найти проблемы, всегда что-нибудь найдёт. Только корректность, три раунда. |
| Не пишите проектные скиллы заранее и не добавляйте своих агентов, хуки или своды правил | Скилл вырастает из задачи, которую проект решил; всё остальное оплачивается на каждом ходу. |
| Не заводите журнал сессий, если проект его не ведёт | Он дублирует спеку, ADR и git. |
| Не храните сданные спеки или папку-архив «для справки» | Сессии читают их как действующие требования; историю хранит git. |

## Признаки, что всё работает

- Каждая сессия начинается с `/harness:start`, и вы не гадаете, что вводить дальше.
- Сессии задают вопросы до написания кода — о вашей предметной области, а не об очевидном.
- Для каждого нетривиального изменения есть спека, и ваш интерфейс в ней слово в слово.
- Каждое «готово» приходит с командой и её выводом.
- Когда вы один раз называете решение, ADR появляется сразу, а не в конце сессии, и следующая сессия
  ссылается на него без напоминания.
- В `specs/` лежит только открытая работа, а каждое ADR, заменённое более новым, говорит об этом в
  своём статусе.
- Повторяющиеся задачи стали проектными скиллами, и их прогоны становятся короче.
- `CLAUDE.md` со временем становится короче, а не длиннее.

Если какой-то признак регулярно не выполняется и с введённой командой, это находка про обвязку —
сообщите о ней, а не добавляйте правила.

## Поддержка

- **Раз в 3–6 месяцев или после смены модели:** скажите `audit my Claude Code harness`. Скилл первым
  делом сообщит, что вырезать; вырезать важнее, чем добавлять.
- **Плагины:** автообновление, как настроено выше, или обновление вручную через
  `claude plugin update <plugin>@<marketplace>`.
- Никогда не закрепляйте версию модели или Claude Code в файлах проекта.
