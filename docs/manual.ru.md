# Мануал — работа по обвязке

[English](manual.md) · **Русский**

Что вводить, когда и что проверять — от первой установки до шестого месяца проекта. Сама обвязка
маленькая: `CLAUDE.md` с блоком *How we work*, список запретов и инструменты процесса из
[mattpocock-skills](https://github.com/mattpocock/skills). Эта страница — поток, который из них
складывается.

Думайте **потоками, а не скиллами**. Есть один основной поток — для изменения, которое помещается
в одну сессию, — и несколько ответвлений: работа на несколько сессий, большая неясная задача, баг,
задачи, которые приходят от других людей. Каждый раздел даёт строки, которые вводить.

Строки интервью, ревью и исправлений — те самые промпты, которые измерялись; строки тестов и сборки
переносят измеренные промпты (для целой спеки) на один тикет. На стенде скрипт защищал тесты от
записи во время сборки; здесь вместо него — правило запрета плюс проверка `git diff`. Блок *How we
work* просит каждую сессию идти тем же потоком без подсказок, и это само по себе не измерено: если
сессия пропускает шаг, введите его строку отсюда.

**Строки для ввода оставлены на английском** — в таком виде они измерялись. Писать их по-русски
можно, но этот вариант не проверялся.

## Установка

**Один раз на машину.**

```
/plugin marketplace add nikitaCodeSave/claude-code-harness
/plugin install harness@claude-code-harness
/plugin install mattpocock-skills --marketplace mattpocock/skills
```

То, что вы ставите из `/plugin`, начинает действовать, когда закрывается его меню.

В README Pocock есть ещё путь через официальный каталог, `mattpocock-skills@claude-plugins-official`.
Выберите один путь. Не копируйте скиллы в проект ещё и через skills.sh и не включайте плагин в
аккаунте claude.ai, который синхронизирует его в терминальные сессии как `mattpocock-skills@synced`:
в обоих случаях каждый скилл окажется дважды.

Затем в **пользовательских** настройках (`~/.claude/settings.json`):

```json
{
  "permissions": { "deny": ["Skill(mattpocock-skills:tdd)"] },
  "extraKnownMarketplaces": {
    "claude-code-harness": {
      "source": { "source": "github", "repo": "nikitaCodeSave/claude-code-harness" },
      "autoUpdate": true
    },
    "mattpocock": {
      "source": { "source": "github", "repo": "mattpocock/skills" },
      "autoUpdate": true
    }
  }
}
```

Запрет блокирует `/tdd` и по короткому имени, поэтому `/implement` собирает без него. `autoUpdate`
включает обновления для стороннего маркетплейса — по умолчанию они выключены. Если в ваших
настройках задан `DISABLE_AUTOUPDATER`, `DISABLE_UPDATES` или
`CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, автообновление плагинов выключено, пока вы не добавите
`"FORCE_AUTOUPDATE_PLUGINS": "1"` в `env`. Так сам Claude Code остаётся на своей версии, а плагины
обновляются. Обновление идёт в фоне интерактивной сессии и загружается в следующей. Добавьте эти
ключи в существующий файл, не заменяйте его.

**Один раз на проект.** Откройте Claude Code **в корне репозитория** и скажите:

> set up Claude Code harness in this project

Скилл прочтёт репозиторий, выберет путь (новый / существующий / с обвязкой), спросит только то,
чего не видно из кода, и передаст работу. Затем один раз запустите `/setup-matt-pocock-skills`: он
запишет трекер (GitHub, GitLab или локальные файлы), метки триажа и где лежат доменные документы.

**Каждая сессия стартует из корня репозитория.** Список запретов из `.claude/settings.json`
читается из каталога, где стартует сессия. Сессия, запущенная внутри пакета, работает без него.

## Основной поток — изменение, которое помещается в одну сессию

```
описание + строка интервью  →  ответы на вопросы  →  файл спеки  →  сборка в той же сессии
        →  «готово» с командой и выводом  →  /code-review  →  коммит
```

**1. Опишите изменение и попросите интервью.**

```
<what you want, in your words; any interface you have already fixed — module, signature, error type>

Interview me until you could write the spec, then write it to specs/<slug>.md. The spec says what
and why (acceptance criteria as checkable statements, non-goals), not how. Copy any interface my
request fixes (module paths, signatures, error classes) into it verbatim. Then build it. Done means
the test suite passes and the spec's criteria are covered; report the command and its output.
```

Первую строку — что вы хотите и какой интерфейс уже зафиксирован — пишите своими словами, на любом
языке. Если `/setup-matt-pocock-skills` задал место для спек в блоке *Agent skills*, используйте
его.

**2. Отвечайте на вопросы.** Здесь уходит ваше время, и именно этот шаг окупается. Если владелец не
правит итоговый отчёт агента: без интервью полная приёмка в 3 из 9 прогонов, с ним — в 7–9 из 9.
Владелец, который правил отчёт, получал 5 из 9 без интервью — за счёт того, что правил сам.
Решения «на будущее» называйте сейчас, один раз: сессия запишет их в ADR, и следующие сессии их
прочтут.

**3. Просмотрите спеку, когда она появится.** Проверьте три вещи:
- зафиксированный вами интерфейс записан слово в слово;
- non-goals — ваши;
- каждый критерий — то, на чём тест может упасть.

Поправьте сейчас — это самый дешёвый момент. Одна выпавшая строка интерфейса однажды обнулила набор
приёмочных тестов.

**4. Дайте собрать в той же сессии.** Не делайте `/clear` между спекой и сборкой. Та же сессия
держала полную приёмку в 8 из 9 прогонов — самый дешёвый поток с таким результатом. Свежая сессия,
собирающая только по файлу, — 7 из 9. Один исполнитель — никакого веера субагентов на изменении
такого размера.

**5. Прочтите «готово».** В нём должны быть команда и её вывод. «Тесты проходят» без вывода — это
не готово:

```
Show the command you ran and its output.
```

**6. Ревью по уровню риска.**

- **Обычное изменение:** `/code-review` на дифф. На среднем effort он сообщает ещё и о чистке кода и
  о соглашениях из `CLAUDE.md`; исправляйте то, что влияет на корректность, остальное — по желанию.
- **Рискованное изменение** — безопасность, миграции, парсеры, инварианты, всё, что «выглядит
  готовым» и дорого обойдётся, если неверно: его ревьюит **отдельная сессия только для чтения**
  против спеки.

  ```
  claude --permission-mode plan
  ```

  План-режим защищает от записи, только если в этой сессии недоступен обход прав (нет
  `--dangerously-skip-permissions`, нет `bypassPermissions` по умолчанию); иначе Claude Code один
  раз об этом скажет, и правки пройдут.

  ```
  Review the changes since commit <base> (committed and uncommitted) against specs/<slug>.md.
  Report only gaps that affect correctness, each with file:line; skip style. If there is nothing
  to fix, say so.
  ```

  Вставьте находки обратно в сессию сборки. Держите её открытой в другом терминале или запустите
  `claude --resume` и выберите её; `--continue` открыл бы сессию ревью.

  ```
  A fresh reviewer who has not seen your reasoning reported:
  <findings>
  Reproduce each finding before changing anything; fix the real ones and reject the rest in one
  sentence each. Report the command and its output.
  ```

  Не больше трёх раундов. Четвёртый означает, что неверен подход, — остановитесь и пересмотрите
  его.

**7. Коммит.** Сообщение говорит, что изменилось и почему. Решения живут в ADR, текущая работа — в
спеке или трекере, история — в git.

## Работа не на одну сессию

Этим потоком пользуйтесь, только когда работа действительно не помещается в одну сессию. Признаки:
- сессия сама так говорит (блок *How we work* просит её об этом);
- в спеке несколько независимых результатов;
- контекст заполняется ещё до начала сборки.

На фичах, помещавшихся в одну сессию, поток по тикетам (без сессии с тестами, описанной ниже) стоил
в 11 раз дороже основного потока, потребовал впятеро больше ходов владельца и потерял решение —
поэтому он для работы, которая действительно не помещается.

**1. Интервью как выше, затем остановитесь до сборки.**
- С трекером: завершите тот же разговор командой `/to-spec`. Она пишет спеку из разговора в трекер,
  так что `specs/<slug>.md` уже не нужен.
- Без трекера: пусть сессия напишет `specs/<slug>.md`.

Затем в том же контексте:

```
/to-tickets
```

Каждый тикет — вертикальный срез, рассчитанный на одну свежую сессию, с объявленными блокерами.

Прежде чем уйти из этого контекста, убедитесь, что каждое решение записано в ADR:

```
Which decisions from this conversation are not yet in an ADR? Write them.
```

Решение, записанное где угодно, кроме ADR, — даже заметкой «вне рамок» в спеке, — могут переспросить
в следующей сессии и снять, если владелец о нём забыл; ADR читается до начала работы.

**2. На каждый тикет — две сессии.**

*а. Сначала тесты, в отдельной сессии* (`/clear` или новый терминал):

```
Read ticket <ref>. Turn every acceptance criterion into tests under tests/acceptance/<ticket>/,
exercising only the public interface the ticket names. Take expected values from the ticket, not
from the code. Do not implement the feature: these tests should fail for now. Report the command
you ran and its output.
```

Посмотрите, *как* они падают. Каждый тест должен падать на своём assert, а не на ошибке импорта.
Только это показывает, что критерий вообще может не выполниться: `/to-tickets` иногда пишет
критерий, который выполнен уже на базовом коммите. Затем закоммитьте тесты.

*б. Сборка в свежей сессии, где эти тесты закрыты на запись:*

```
claude --settings '{"permissions":{"deny":["Edit(./tests/acceptance/**)","Bash(chmod:*)"]}}'
```
```
/implement <ref>
tests/acceptance/<ticket>/ is the agreed check and is read-only for you. Done means it and the
existing suite pass; report the command and its output. If a test looks wrong, say so — do not
work around it.
```

`/implement` коммитит в текущую ветку и не закрывает тикет. Закройте его сами, иначе
заблокированные им тикеты так и не станут готовыми к работе. Запрет останавливает инструменты
правки и распознаваемую запись из shell (перенаправления, `tee`, `sed -i`), но не скрипт, который
сам открывает файл, поэтому проверьте, что тесты не тронуты:

```bash
git diff --stat <tests-commit> -- tests/acceptance/    # ничего не печатает
```

*в. Ревью по уровню риска*, как в основном потоке.

Почему две сессии: приёмочные тесты, написанные по спеке отдельной сессией и закрытые для
исполнителя на запись, дали лучший измеренный результат (9 из 9). На уровне тикета это расширение
того результата; отдельно оно не измерено.

**Один тикет за раз.** `/implement-spec` собирает готовые тикеты параллельно. В лаборатории
пайплайн, запускавший 12–22 субагента вместе с грилингом, тикетами и `/tdd`, стоил в 3.1–4.4 раза
дороже последовательного потока при той же приёмке (эти факторы не разделены); контролируемое
внешнее исследование, где параллельность изолирована, показало, что параллельные субагенты решают
ограниченные задачи хуже.

## Другие ситуации

| Что у вас | Что вводить | Пояснение |
|---|---|---|
| Большая задача, путь к которой пока не виден | `/wayfinder` | Составляет тикеты-решения и разбирает их по одному. Планирует, но не собирает. Дальше — поток выше. |
| Баг | `Reproduce this with a failing test first and show it failing; then fix it and show the same test passing.` | Это диагностика, а не ритуал test-first. На трудном баге агент может сам подключить `diagnosing-bugs`. |
| Баг-репорты и запросы от других людей | `/triage` | Тикетам, которые вы сгенерировали сами, там не место. |
| Сессия далась тяжелее, чем следовало | `/retro` | Предлагает проверки и указатели для окружения; выбираете вы. Проверка, которая может упасть, лучше новой строки прозы. |
| Вопрос дизайна, который разговором не решить | попросите одноразовый прототип | `prototype` вызывается моделью. |
| Проблема в самом языке предметной области | `/grill-with-docs` | Строит `GLOSSARY.md` и ADR по ходу. Для обычных знаний не нужен — их покрывают правила в `CLAUDE.md`. |
| Кодовая база похожа на кашу | `/improve-codebase-architecture` | Обзор с кандидатами; каждый возвращается в основной поток. Здесь не измерялся. |
| Непонятно, что из этого подходит | `/ask-matt` | Маршрутизирует по скиллам Pocock. |

## Знания между сессиями

Проекту, над которым работают месяцами, нужно, чтобы каждая новая сессия начиналась с его языка и
его решений, а не с первого разговора. Обвязка держит их в версионируемых файлах:

- **Термины** → `GLOSSARY.md` или `GLOSSARY-MAP.md` со ссылками на глоссарий каждого bounded
  context. Термин добавляется при первом использовании или когда о нём договорились.
- **Решения**, которым должна следовать дальнейшая работа, включая сказанные «на будущее» →
  `docs/adr/` или журнал решений, который проект уже ведёт. Записываются в той сессии, где приняты.
- **Перед изменением области** сессия читает статьи глоссария и ADR, которые её касаются.
- **Текущая работа** живёт в открытой спеке или трекере. Больше нигде.

В конце сессии, где что-то решили, спросите:

```
Which ADRs and glossary entries did you write this session?
```

Что измерялось: три фичи в новых сессиях, владелец ни разу не повторял прежних решений.
- Передовая модель сохранила их в 3 из 3 прогонов и без этих правил — записала сама.
- С правилами — тоже 3 из 3, примерно на 17% дороже.
- В одном дымовом прогоне более слабая модель выдержала 8 из 19 проверок без правил и 18 из 19 с
  ними.

Так что правила — страховка. Месяцы накопления — десятки фич, разрастающийся файл спеки — не
моделировались.

## Контекст на границах фаз

| Граница | Что делать |
|---|---|
| Интервью → спека → сборка | Продолжать в той же сессии (измерено выше). |
| `/to-spec` → `/to-tickets` | Продолжать — один контекст. |
| Сессия тестов → сессия сборки | Новая сессия: исполнитель не должен сам писать свой оракул. |
| Тикет → следующий тикет | Новая сессия; каждый тикет самодостаточен. |
| Сборка → рискованное ревью | Отдельная сессия только для чтения. |
| Сессия ждёт | Большая сессия, простоявшая около часа (например, сессия сборки во время долгого ревью), сжимается сама; вернувшись, введите `Re-read specs/<slug>.md before continuing.` или отключите это в `/config` → Idle compaction. |
| Контекст разрастается | В середине фазы — продолжайте или отдайте ограниченный кусок субагенту. На границе — лучше продолжить или `/clear`; `/compact` — последний вариант (`ask-matt` у Pocock). После любого сжатия введите `Re-read specs/<slug>.md before continuing.` Рамки задачи хранятся в файле спеки, потому что, по сообщениям, сжатие теряет их чаще, чем требования, — это одно внешнее исследование, здесь не проверенное. |
| Работа переходит к коллеге, в другой каталог или в другую обвязку | `/handoff`. |

## Большие многосоставные репозитории

- **Стартуйте из корня.** `CLAUDE.md` компонента загружается, когда работа касается его каталога,
  так что его команды и инварианты ничего не стоят в остальное время.
- **Контракты между компонентами — самый рискованный шов.** Изменить контракт — значит сначала
  записать ADR и обновить проверку, которую запускают обе стороны. Пути контрактов в настройках —
  под `ask`.
- **Тикеты остаются вертикальными срезами**, даже если результат затрагивает несколько
  компонентов. Не режьте их по компоненту за раз.
- **Командам:** держите короткий `REVIEW.md` от владельцев кода. В нём — как здесь выглядит провал,
  какие пути всегда требуют человека и лимит на мелочи. Держите его обычным файлом: сервис ревью
  пропускает файл-симлинк и обрезает файл сверх лимита размера.
- **Кто ревьюит, определяет риск, а не автор** (по описанию того, как ревьюит команда Claude Code
  в Anthropic):

  | Риск | Ревьюеры |
  |---|---|
  | Низкий | Зелёные автоматические проверки |
  | Средний | Один человек |
  | Высокий | Два человека |

  Чувствительные пути и CI-процессы всегда требуют человека. Человек, направлявший агента, считается
  одним из ревьюеров; одобрение агента за одобрение человека не считается.

## Не делайте

| Не делайте | Почему |
|---|---|
| Не используйте `/tdd` и не предписывайте исполнителю red-green-refactor | Поток без этого ритуала дал mutation score в пределах 0.05 от пайплайна с `/tdd`. В его наборе были приёмочные тесты из отдельной сессии, так что сравнение — «независимые тесты без ритуала» против «ритуала». Внешнее исследование не нашло выигрыша от test-first при расходе токенов в 3–8.5 раза больше. Тесты, заранее написанные *другой* сессией (выше), и падающая проверка до исправления бага — это не тот ритуал. |
| Не используйте поток по тикетам для работы на одну сессию | В 11 раз дороже, впятеро больше ходов владельца и одно потерянное решение (выше). |
| Не запускайте параллельных исполнителей на ограниченном изменении | См. «Один тикет за раз». |
| Не собирайте в свежей сессии только по файлу спеки | 7 из 9 против 8 из 9 в сессии, которая её писала. Если нужна свежая — сначала напишите приёмочные тесты (9 из 9). |
| Не принимайте «тесты проходят» без вывода | Это заявление, а не доказательство. |
| Не продолжайте ревью, пока ревьюер не будет доволен | Ревьюер, которого просят найти проблемы, всегда что-нибудь найдёт. Только корректность, три раунда. |
| Не добавляйте своих агентов, хуки или своды правил | Обвязка намеренно маленькая; каждое добавление оплачивается на каждом ходу. Запустите `/retro` и предпочтите проверку. |
| Не заводите журнал сессий, если проект его не ведёт | Он дублирует спеку, ADR и git. |

## Признаки, что всё работает

- Сессии задают вопросы до написания кода — о вашей предметной области, а не об очевидном.
- Для каждого нетривиального изменения есть спека, и ваш интерфейс в ней слово в слово.
- Каждое «готово» приходит с командой и её выводом.
- Когда вы один раз называете решение, в той же сессии появляется ADR, и следующая сессия ссылается
  на него без напоминания.
- На ограниченных изменениях нет веера субагентов, а ревью заканчивается за три раунда.
- `CLAUDE.md` со временем становится короче, а не длиннее.

Если один из признаков регулярно не выполняется, вводите строку этого шага отсюда. Если он не
выполняется и с введённой строкой, это находка про обвязку — сообщите о ней, а не добавляйте
правила.

## Поддержка

- **Раз в 3–6 месяцев или после смены модели:** скажите `audit my Claude Code harness`. Скилл
  первым делом сообщит, что вырезать; вырезать важнее, чем добавлять.
- **Плагины:** автообновление, как настроено выше, или обновление вручную через
  `claude plugin update <plugin>@<marketplace>`.
- Никогда не закрепляйте версию модели или Claude Code в файлах проекта.
