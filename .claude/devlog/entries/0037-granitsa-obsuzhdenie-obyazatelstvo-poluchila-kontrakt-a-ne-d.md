# Граница «обсуждение → обязательство» получила контракт, а не документ

## Контекст

Оператор указал на самую слабую часть кита: всё, что происходит ДО кода — подготовительные
работы, обсуждение задачи до её попадания в бэклог, ведение очереди, фиксация. Поводом стал
догфудящий проект (Greenplun-router-runtime), который за июль–август сам вырастил planning-слой
и дважды его переделал: аудит #149 нашёл расходящиеся регистры, ложную active/blocked картину и
чужой незакоммиченный WIP в дереве; #151 ввёл lifecycle планов, DoR и механический tracking-checker;
`9df79f5` снёс −2939 строк, удалив параллельный `.claude/progress/` и три verbatim-документа кита
(`.claude/docs/{workflow,testing,docs-discipline}.md`) как второй источник истины и конкурирующую
инструкцию, и запретил их checker'ом.

Первый дизайн правки был отдельным reference `planning-governance.md` (~150 строк): DoR, lifecycle
плана, очередь, stream-объект, механизация. Он не пережил рефутацию свежим контекстом другого
вендора (Codex, два раунда). Два убийственных возражения оказались верны при проверке:
`harness-evolution.md:47` требует fold **в существующий** reference — «not a new file and not a new
layer»; и примерно две трети дизайна уже жили в ките (closure — `workflow.md:123`, альтернативы с
ценой — `workflow.md:40`, ADR-порог — `docs-discipline.md:28`, carrier-правило —
`harness-discipline.md:171`). Осталась чистая дельта, и она вошла в существующие файлы.

## Изменения

**Intake-контракт (Phase 5 item 2).** Все правила ниже управляют уже выбранной работой; ни одно не
говорит, как предложение становится работой. Открытый acceptance-вопрос означает, что фича не
готова к взятию: вопрос → датированный ответ → на чём ответ держится. Кодированная таблица опций —
только когда прочтения различаются ценой. Агент не ратифицирует за владельца; молчание не согласие.
Ратифицированное решение не есть работа: `wontfix` и «ратифицирует текущее поведение» терминальны и
записи в ledger не создают. Открытый вопрос блокирует implementation-фичу, но НЕ ограниченный spike,
который на него отвечает, — иначе discovery запрещён вопросом, ради которого существует; «ограниченный»
— это условие (обратимо, без прод-данных, без трат), а не ярлык. Внешний трекер — канон, ledger несёт
только ID, и сессия обязана проверить, что этот канон читаем.

**`priority` в каноне ledger.** Ритуал в трёх местах требовал «highest-priority», а поля не было —
порядок массива работал под чужим именем. Меньше = раньше, ties по порядку массива, отсутствие
сортируется в хвост. `F0` greenfield получил `priority: 0`: запись, на которую сессия обязана сесть
первым ходом, не может сортироваться последней.

**Write-through, потому что рабочая сессия не читает чеклист.** Правило intake добавлено в
`features.json.rules` шаблона, а Phase 7 получил проверку `grep -ci '"priority"'` +
`grep -ci 'question'` по ledger — та же логика, что у CLAUDE.md-грепов рядом.

**Session-start ritual (item 4).** Два чека: у взятой фичи нет открытого acceptance-вопроса;
грязные code/test/ops-пути принадлежат ей или названы в `notes`. Провенанс — аудит #149 Greenplun:
незакоммиченный второй comparator, зелёный под своим focused-тестом, лежал в дереве, не принадлежал
ни одному плану, и живой план его прямо запрещал.

**Audit: покрытие вместо наличия файла + §11.** Отсутствие shipped-docs — finding только там, где
duty-области именно этого файла не покрыты (списки duty-областей разведены по трём файлам).
Противоречие shipped-строки проектному канону — finding всегда, и решает его оператор: локальный
текст не автоматически прав (проектное правило, отменяющее инвариант кита, — finding против проекта).
Новая §11 «Ledger & intake» — две фальсифицируемые проверки, целиком пропускается без ledger; это
reachability для зрелых проектов, куда правки Bootstrap не доедут.

**Fail-open как класс дефекта** (`harness-discipline.md`, рядом с «mechanical invariants»): гейт,
который не смог отработать, не должен читаться как pass. Провенанс — `_changed_paths` в чекере
Greenplun возвращает `[]` при ненулевом `git status`, после чего проверка незарегистрированного WIP
проходит по построению. Плюс: зелёный гейт доказывает только то, что парсит.

**Нативный task-list vs ledger** (`native-capabilities.md`): координация текущего прогона,
machine-local, не repository-owned регистр обязательств.

**operator-playbook**: буллет «Ratify what only you can decide» в build ritual и сужение строки
«no upfront questionnaire» — исключение составляют вопросы, меняющие смысл слова «правильно».

**evidence-base**: GitHub Spec Kit (T4) как независимое подтверждение, что pre-implementation
ambiguity gate — реальный пробел (`/speckit.clarify` и `/speckit.checklist` выполняются ДО
`/speckit.plan`); явно НЕ источник формулировок кита.

**Не сделано сознательно:** новый reference-файл; lifecycle `draft/ready/active` рядом с
`passes`/`blocked`; per-owner WIP-лимит; правило «закрытые записи уходят из ledger»;
**stream-объект** — двойной триггер под него оказался циркулярным (чтобы понять, что фокус
переключается между направлениями, направления уже надо считать объектами), а весь провенанс —
один проект, который завёл workstream-файл и затем его удалил.

## Проверка

- Рефутация свежим контекстом другого вендора (Codex, thread `019fc98f`), два раунда: дизайн → no-go
  (новый файл против `harness-evolution.md:47`, дублирование, streams без провенанса) → реализация →
  список дефектов, из которых подтверждены и исправлены: `needs-decision` вне собственного enum,
  `F0` без priority при правиле «missing sorts last», intake против «small → acceptance only»,
  ledger одновременно «только обязательства» и хранилище терминальных исходов, ложный finding §11
  для проектов с внешним трекером, конфликт audit-правила с `testing.md:7`, «every dirty path»
  шире собственного провенанса, teammate-претензия против shared team list.
- Переутверждения, снятые собственной проверкой до вердикта: Kiro как источник (страница не
  подтверждает гейт между фазами), «comparator засчитали за прогресс» (в devlog #149 сказано, что
  аудит его отделил), «observed» для fail-open (доказан латентный дефект кода, не произошедший
  инцидент), «five questions produced two implementations» (их три: E1, E3, E5).
- `python3 -c "…json.loads(…)"` по JSON-примеру шаблона → валиден, поля
  `id/priority/title/description/verify/passes/preconditions`, 4 правила в `rules`.
- `rebuild-index.py .claude/devlog` → зелёный (валидирует slug и frontmatter этой записи).

Non-claims: правки только документационные — ни один агент, хук, скилл или скрипт не менялся.
Перенос механического checker'а из Greenplun не выполнялся и не предлагается: 711 строк Python ради
валидации Markdown, с fail-open и без парсинга очереди. Заявленная граница получила контракт и
write-through, но не схему объектов «вопрос → решение → фича»; promotion-механика и carrier для
терминальных исходов без внешнего трекера остаются открытыми.
